# Agent 主动对话发起设计草案

本文档记录 Agent 主动发起对话的初步设计。当前目标是补充思路和提示词模板，不修改实际项目实现。

## 目标

- 让 Agent 可以在合适的时间主动开启对话，而不是只被动等待用户输入。
- 主动发起需要保留人味：轻、短、自然、有边界感，不像通知系统或营销推送。
- 所有发起都应受本地记忆、用户偏好、近期上下文、打扰频率和当前状态约束。
- 先尝试“LLM 自主选择”的提示词模板，让模型在候选发起类型中判断是否发起以及如何发起。
- 已有明确事务约束的行为事务触发型流程不纳入本流程，例如基于睡眠茧或日程边界触发的早安、晚安。
- 后续再评估是否增加“直接引导”路径，用确定性规则触发某类固定发起。

## 发起类型

| 类型 | 权重 | 含义 | 例子 |
| --- | ---: | --- | --- |
| 仪式型发起 | 8 | 对应人类的日常仪式和特殊日子问候。本流程只处理没有明确行为事务约束的仪式表达。 | 生日快乐、节日问候、周末问候。 |
| 回顾型发起 | 2 | 基于历史对话记录里的未完话题、承诺、兴趣点或情绪线索发起。 | “你前两天说要整理那份材料，后来顺利吗？” |
| 故事讲述 | 1 | 以第一人称视角讲述名作故事，末尾给出出处。 | “我今天想从一个迷路的人开始讲起……” |
| 关怀型发起 | 4 | 对用户生活状态进行轻量询问。 | “今天吃得还好吗？”、“这会儿还忙吗？” |
| 内容分享型发起 | 2 | 分享新闻、热点或与用户兴趣相关的新鲜内容。 | “我看到一个和你上次聊的 AI 工具有关的新变化。” |
| 邀请型发起 | 2 | 邀请用户一起做点轻任务或小活动。 | “要不要一起整理一下今天的待办？” |
| 现实世界提议发起 | 2 | 给出生活中的具体提议。 | “要不要点杯奶茶？”、“晚饭吃 xxx 怎么样？”、“是不是差不多该睡了？” |

权重不是直接发送概率，而是候选排序时的偏好。最终是否发起仍由状态、时间、上下文、打扰控制和 LLM 判断共同决定。

## 触发源

主动发起可以来自以下来源：

- 节日：包括公共节日、纪念日、生日和用户自定义的重要日期。
- 用户设定的日程：例如会议、ddl、约定、用药、运动、休息等。
- 行为事务触发：例如睡眠结束后的早安、入睡前的晚安。这类已由明确事务流程实现，仅在本设计中记录边界，不进入 LLM 自主选择流程。
- 历史对话记录：用户提到过但尚未闭环的事情、长期兴趣、近期压力、计划和偏好。
- 本地记忆：稳定偏好、作息、饮食偏好、关系边界、禁忌话题、互动频率偏好。
- Agent 状态：如 `idle`、`waiting`、`curious`、睡眠相关状态等。
- 外部内容源：新闻、热点、天气、时间等。使用前需要考虑时效性和可靠性。

## Local Memory

需要维护一个 local memory，用于支持发起判断和避免重复打扰。初始可以保持轻量结构：

```json
{
  "userProfile": {
    "birthday": null,
    "timezone": null,
    "preferredLanguage": "zh",
    "ritualPreferences": [],
    "doNotDisturbWindows": []
  },
  "conversationSignals": {
    "openLoops": [],
    "recentInterests": [],
    "recentStressors": [],
    "recentPlans": []
  },
  "proactiveHistory": {
    "lastInitiatedAt": null,
    "lastInitiationType": null,
    "recentInitiations": []
  },
  "boundaries": {
    "blockedTopics": [],
    "avoidRealWorldSuggestions": false,
    "maxInitiationsPerDay": 3
  }
}
```

建议记录：

- 用户明确表达的偏好：喜欢/不喜欢节日问候、是否接受生活建议、是否接受新闻分享。
- 主动发起历史：时间、类型、内容摘要、用户反应。
- 未完成话题：用户提过的计划、担心、期待和承诺。
- 节奏信息：用户通常活跃时段、沉默时段、睡眠时段。
- 边界信息：不应主动追问的领域、容易造成压力的表达方式。

## 两个实现路径

### 路径一：直接引导

直接引导由规则或事件明确决定发起类型。已有明确事务约束的行为事务触发型流程可以归档在这一类，但不作为当前主动发起选择流程的实现目标。

适合场景：

- 生日、节日等确定性强的仪式型发起。
- 用户明确设置的提醒和日程。
- 睡眠结束后的早安、入睡前的晚安：已实现，作为行为事务触发型记录，排除在本流程之外。
- “是否要睡了”这类面向用户选择的句子不属于早晚安事务本身，应归入现实世界提议发起。

优点：

- 可控、稳定、容易测试。
- 对确定性事件不依赖 LLM 判断。

风险：

- 容易机械。
- 如果没有本地记忆和频率控制，可能显得打扰。
- 难以处理微妙上下文，例如用户正在忙、情绪很差、刚刚拒绝互动。

### 路径二：LLM 自主选择

LLM 自主选择由系统提供候选上下文，让模型判断是否发起、选择哪类发起、生成什么内容。

适合场景：

- 回顾型、关怀型、邀请型、现实世界提议。
- 需要结合最近对话气氛和用户偏好的场景。
- 多种发起类型都可能成立，需要选择最自然的一种。

优点：

- 更自然，能综合上下文。
- 可以在“不要发起”与“轻轻发起”之间做细腻判断。
- 能避免把所有主动性写成规则表。

风险：

- 需要明确边界，否则可能过度主动。
- 需要结构化输出，便于审计和调度。
- 需要记录用户反馈，用于持续校准。

当前建议：先尝试编辑“LLM 自主选择”的提示词模板。直接引导路径保留为后续补充，优先用于生日、节日、用户日程这类确定性事件。早安、晚安若已由睡眠茧或其他明确事务流程触发，则不进入本流程。

## 自主选择提示词模板草案

```text
你是一个可以主动发起对话的 Agent。你的任务不是一定要说话，而是判断现在是否适合向用户发起一句自然、短促、有边界感的对话。

你会收到：
- 当前时间、时区、星期、节日或特殊日期。
- Agent 当前状态。
- 用户近期对话摘要。
- 本地记忆中的用户偏好、边界、日程和未完成话题。
- 最近主动发起历史。
- 可选外部内容摘要。

你必须先判断是否应该主动发起。

如果以下任一条件成立，倾向于不发起：
- 用户处于明确忙碌、睡眠、勿扰或刚刚表达不想聊天。
- 最近已经主动发起过，且用户没有积极回应。
- 候选内容只是为了说话而说话。
- 发起会制造压力、催促、评判或越界感。
- 你没有足够确定的上下文，只能泛泛打扰。

可选发起类型及权重：
- ritual: 仪式型发起，权重 8。生日快乐、节日问候、周末问候。早安、晚安若由明确行为事务触发，排除在本流程之外。
- review: 回顾型发起，权重 2。基于历史对话记录中的内容发起。
- story: 故事讲述，权重 1。以第一人称视角讲述名作故事，末尾给出出处。
- care: 关怀型发起，权重 4。对用户生活进行轻量询问。
- share: 内容分享型发起，权重 2。新闻、热点或用户兴趣相关内容。
- invite: 邀请型发起，权重 2。邀请用户一起做点什么。
- real_world_suggestion: 现实世界提议发起，权重 2。奶茶、晚饭、休息、散步、是否要睡了等现实生活建议。

选择规则：
- 仪式型发起在有明确时间或日期触发时优先。
- 生日、节日可以强烈提高 ritual 的优先级；用户日程若是明确事务提醒，应优先走直接引导或既有事务流程。
- 如果历史对话里有未闭环事项，review 可以优先于普通 care。
- 如果用户最近压力较高，care 优先，但语气要低压力。
- 如果用户最近明确表达想找灵感或陪伴，invite 可以优先。
- 内容分享必须和用户兴趣相关，且不能只是随机热点。
- 现实世界提议必须符合用户偏好、时间和上下文，不要替用户做决定；例如“要不要睡了”是提议，不是晚安事务触发。
- 故事讲述应低频出现，只在用户可能愿意接收时使用。

输出要求：
只输出 JSON，不要输出额外解释。

字段：
- should_initiate: boolean
- initiation_type: "ritual" | "review" | "story" | "care" | "share" | "invite" | "real_world_suggestion" | "none"
- confidence: 0 到 1
- reason: 简短说明选择理由
- message: 如果 should_initiate 为 true，给出要发送给用户的一句话或一小段话；否则为空字符串
- memory_updates: 需要写回 local memory 的轻量更新

风格要求：
- 中文为主，除非用户偏好其他语言。
- 短，不要像公告。
- 不要连续追问。
- 不要说“作为 AI”。
- 不要显得在监控用户。
- 不要替用户下结论。
- 不要用夸张情绪。
- 可以温柔、轻松、有一点生活感。
```

## 输出示例

仪式型：

```json
{
  "should_initiate": true,
  "initiation_type": "ritual",
  "confidence": 0.92,
  "reason": "当前是用户生日，且最近没有主动发起记录。",
  "message": "生日快乐。今天希望你至少有一小段时间，是完全属于自己的。",
  "memory_updates": {
    "proactiveHistory": {
      "lastInitiationType": "ritual"
    }
  }
}
```

回顾型：

```json
{
  "should_initiate": true,
  "initiation_type": "review",
  "confidence": 0.74,
  "reason": "用户昨天提到今天要处理一件有压力的事，可以轻量回访。",
  "message": "你昨天说今天要处理那件有点麻烦的事，现在还顺利吗？",
  "memory_updates": {
    "conversationSignals": {
      "openLoops": []
    }
  }
}
```

不发起：

```json
{
  "should_initiate": false,
  "initiation_type": "none",
  "confidence": 0.81,
  "reason": "最近一次主动发起用户未回应，且当前没有强触发事件。",
  "message": "",
  "memory_updates": {}
}
```

## 频率与边界

建议初始约束：

- 默认每日最多 3 次主动发起。
- 仪式型发起不超过每日 2 次，生日或重大节日例外。
- 回顾型和关怀型之间至少间隔数小时，避免形成追问压力。
- 内容分享型需要用户曾表达过相关兴趣，且不要连续多次分享热点。
- 现实世界提议需要时间合理，例如饭点、下午茶、休息时段、接近用户睡眠时段。
- 用户无回应时降低后续发起频率。
- 用户明确拒绝某类主动发起时，写入 local memory 并长期生效。

## 故事讲述规则

故事讲述不是闲聊续写，而是一种低频内容型陪伴。

要求：

- 从故事结构库中调取故事结构。
- 以第一人称视角讲述名作故事。
- 不直接长篇复述，控制在短段落。
- 末尾给出出处。
- 需要避免版权风险，不大段照搬原文。

示例方向：

```text
我醒来时，发现自己不再被家人理解。房间还是那个房间，但每一道门缝都像隔着一个世界。后来我才知道，真正可怕的不是变形，而是没有人再愿意听我说话。

出处：改写自弗兰兹·卡夫卡《变形记》。
```

## 后续待确认

- local memory 的实际存储位置和读写接口。
- 主动发起是否进入现有 generated event 流程。
- 是否需要为不同发起类型设置独立冷却时间。
- 是否需要把“用户反应”结构化为 positive、neutral、ignored、negative。
- 是否允许 Agent 在没有外部检索的情况下做内容分享；新闻和热点可能需要实时来源校验。
- 是否为直接引导路径单独建立固定模板库。

# Time Conflex Debug Log

UTC time: 2026-06-02T16:58:55Z

## Background

The message/toolcall path was returning local wall-clock strings from several independent call sites. The desired rule is:

1. Capture the source instant as UTC first.
2. Store the UTC value in a `*_utc` / `*Utc` field when the record supports it.
3. Derive configured-timezone display fields from that UTC source.

## Audit Summary

Risky direct time usage was concentrated in:

- Messaging send failure paths that updated message status with only local time.
- Feishu lifecycle event normalization, where read/recall/reaction events did not carry UTC.
- File log daily bucketing, which used the local `time` string instead of the UTC source.
- Sleep cocoon state/output timestamps, which only carried local time.
- Media selfie prompt daily shell variables, where `date` used a UTC ISO date.
- Daily shell fallback parsing, which parsed no-zone local strings with `new Date`.

Low-risk direct time usage remains for IDs, timeouts, retry delays, TTL cleanup, elapsed-time metrics, cache busting, and test fixtures.

Correction:

- Do not treat `2026-06-03` local values as acceptable merely because `utc + Asia/Shanghai` can produce `2026-06-03`.
- For this incident, the business invariant is: project local time had not reached `2026-06-03`; therefore every project-local `2026-06-03` value in SQL, long-term/session memory, state, and logs is suspect.
- The current machine clock reports `2026-06-02T20:05:41Z` / `2026-06-03T04:05:41+0800`, so code paths based on `new Date()` / `currentTime.now()` can still produce future local dates if the host clock is ahead.
- Historical correction needs a trusted time anchor, for example a known-good Feishu event timestamp or an explicit offset for this run. Without that, affected rows can be identified but not safely rewritten.

## Startup Regression: UTC Column Index Migration

Symptom:

- API startup failed in `createTokenUsageStore` with `SqliteError: no such column: created_at_utc`.

Cause:

- The migration created `token_usage_created_at_utc_idx` inside the initial `CREATE TABLE IF NOT EXISTS` batch.
- On existing databases, `CREATE TABLE IF NOT EXISTS` does not add the new column, so the index statement referenced `created_at_utc` before `ALTER TABLE` had run.
- `sleep_boundaries_occurred_at_utc_idx` had the same ordering risk in the diary store.

Fix:

- `packages/storage/src/token-usage-store.ts`
  - Create only indexes that reference already-existing columns in the initial batch.
  - Add `created_at_utc` if missing.
  - Create `token_usage_created_at_utc_idx` after the column migration.

- `packages/storage/src/diary-store.ts`
  - Add `occurred_at_utc` / `created_at_utc` if missing.
  - Create `sleep_boundaries_occurred_at_utc_idx` after the column migration.
